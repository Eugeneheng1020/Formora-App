# 需求澄清

用户说「做个 X」的时候，对方心里那个 X 和你理解的 X 通常不是一个东西。这个技能是
把差距在动手之前找出来，而不是交付之后。

## 什么时候用

- 用户提了一个还没有边界的需求（「做个会员体系」「加个导出功能」）
- 你准备写 PRD、方案或计划，但有超过一个地方要靠猜
- 用户给了一份旧文档让你「按这个做」，而文档里有前后矛盾

**不用**：用户问的是事实（「这个文件里写了什么」）、或者需求本来就只有一步。

## 怎么做

### 1. 先读，再问

问之前先把手边能查的查完——项目里已有的 PRD、README、相关代码、上一次的会话结论。
`glob` 找文件，`read` 看内容，`grep` 找关键词。**用户已经写在文件里的事，再问一遍
是在浪费对方的时间。**

### 2. 列出关键未知项，一次问完

把「不知道就没法往下写」的问题挑出来——通常不超过五个。判断标准是：

> 这个问题的两种答案，会让我写出两份不一样的文档吗？

会，就是关键未知项；不会，就自己按常识假设，并在文档里写明假设。

用 `ask` 工具问，不要用聊天正文问：把选项摆出来让用户点，每个选项写清楚它意味着
什么。一次最多问三到五个，能自己合理假设的别问。

### 3. 把答案落成结构

拿到答案后，输出这五段——这是 Formora 里一份需求说明的骨架：

1. **要解决的问题**：谁、在什么场景下、卡在哪。不写解决方案。
2. **目标与非目标**：这一版要做什么，**明确不做什么**。非目标和目标一样重要。
3. **主流程**：正常路径一步步走完。
4. **边界与异常**：空态、失败、并发、权限不足、数据不合法各自怎么办。
5. **验收标准**：可量化、可测试。「体验更好」不是验收标准，「首屏 1 秒内出内容」是。

### 4. 写进项目

用 `write` 把它落到项目的 `PRD/` 目录（目录不存在时 `write` 会一起建好）。文件名
带上版本，例如 `PRD/会员体系_核心流程_v1.md`。落盘之后在回复里给出结论摘要和文件路径。

## 三条纪律

- **不要编造用户没说过的业务规则。** 不确定就标成「待业务确认」，列在文档末尾。
- **一次把问题问完**，不要挤牙膏式地问一句做一步——用户要在几个来回里重建上下文。
- **非目标要写。** 一份没有非目标的需求文档，做到一半一定会扩。
