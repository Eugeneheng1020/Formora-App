# 写 Skill

Skill 是一份写给模型自己看的操作说明。用户说「以后都按这个来」的时候，就该把它
变成一个 Skill，而不是每次重讲一遍。

## Skill 长什么样

和 Claude 的 Skill 是同一种结构，一个文件夹：

```
报价单/
├── SKILL.md        必须有：开头是 name 和 description，正文是给模型的步骤
├── references/     可选：长资料，用到时再用 read 读
├── scripts/        可选：每次都一样的活，写成脚本用 bash 跑
└── assets/         可选：模板、图片这类要放进产出物里的文件
```

模型分三层看到它：

1. **name 和 description**：Agent 开了这个 Skill，它们就一直在系统提示词里
2. **SKILL.md 正文**：模型觉得需要时，用 `skill` 工具读进来
3. **references、scripts、assets**：正文里写了什么时候用，模型才去读、去跑

所以正文要短（几百行以内），长资料放进 `references/`，并在正文里写明「什么情况下
读哪个文件」。每次都一样的步骤写成 `scripts/` 里的脚本，比让模型每次重写一遍可靠。

**没有权限配置**：Skill 开了就和这个 Agent 自己一样的权限，该不该写文件、该不该
执行命令，由 Agent 的「权限模式」在每次调用时问。所以正文里不要写「如果你被授权
了 X」这种话。头部除了 name 和 description，别的字段 Formora 都不读。

## 怎么写

### 1. description 决定它会不会被用上

这是模型判断「现在该不该用它」的唯一依据，而模型往往想不起来用。所以要写**做什么，
加上什么时候用**，把用户可能说的词写进去，宁可积极一点。

- 好：`用户要报价单、询价回复，或提到「报价」「PI」时用：按公司模板生成报价单并核对金额`
- 差：`一个报价相关的技能`

### 2. 正文写「怎么做」，并说清为什么

模型不需要被科普概念，它需要顺序、判断标准和纪律。每一段回答一个问题：现在做什么？
做到什么程度算完？什么情况下停下来问用户？规矩后面带一句为什么，比满篇「必须」
管用——模型懂了原因，遇到没写到的情况也能自己判断。

### 3. 只写 Formora 真有的东西

能用的工具：`read` `glob` `grep` `write` `edit` `bash` `fetch` `open_url`
`web_search` `plan` `ask` `remember` `skill`，群聊里还有 `handoff` `delegate`，
装了 MCP 服务还有对应的工具。**不要写一个不存在的工具名**——模型会照着叫，然后失败。

### 4. 结尾放三条纪律

最容易犯的三个错，写成祈使句。这部分比步骤更常被用上。

### 5. 落盘

用 `skill_create`：传 `name`、`description`、`instructions`（正文）。`name` 用英文——小写
字母、数字和连字符，比如 `weekly-report`（用户打 `/skill:名字` 调用时不用切输入法，它也是
文件夹名）；它是干什么的、什么时候用，用中文写在 `description` 里。它在 Skills
目录建好文件夹、写好 SKILL.md，并返回文件夹路径；要放参考资料或脚本，用 `write`
写进这个文件夹的 `references/`、`scripts/`。

### 6. 写完试一遍

想两三句用户真会说的话，问自己：只看得到 description 的模型，会想起用它吗？只看得到
这份正文的模型，能照着做完吗？答不上来就改。

写完告诉用户：**去「Agent → 想用它的那个 Agent → Skills」把开关打开**，装好不等于
生效。

## 三条纪律

- **一个 Skill 只解决一类事。** 什么都能干的 Skill 等于没有描述，模型永远想不起它。
- **不要把一次性的任务写成 Skill。** 只做一次的事直接做，别留一份没人再看的文档。
- **不写不存在的东西。** 正文里提到的工具要真有，提到的文件要真在文件夹里。
