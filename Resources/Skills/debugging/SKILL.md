# 排查问题

出了问题最容易犯的错是「看着像这儿，改一下试试」。改对了不知道为什么对，改错了
不知道错在哪，第三次就彻底乱了。

## 什么时候用

- 有报错、有崩溃、有测试失败、有「本来好好的现在不行了」
- 结果和预期不一样，但你还说不出原因

## 怎么做

### 1. 先复现，再动手

说清楚三件事：**什么输入 → 期望什么 → 实际什么**。三件里缺一件，先补齐再往下走。
拿不到实际输出就先想办法拿到——`bash` 跑一遍、`read` 看日志、必要时加一行打印。

### 2. 读证据，不要读印象

- `grep` 找报错原文，**用报错里的字面词去搜**，不要用你转述的说法
- `read` 看出错那一段的完整上下文，不要只看被指到的那一行
- 顺着调用链往上读，直到找到「第一次变得不对」的地方——不是「最后一次报错」的地方
- 先看**最近改了什么**：本来好好的现在不行了，答案常常就在最近的改动里
  （`bash` 跑 `git log -5`、`git diff`）
- 找一个**能正常工作的相似例子**，和出错的这个逐条对比，差异再小也列出来

### 3. 提出一个能被证伪的假设

写成这样：「我认为是 A 导致的，如果是，那么改动 B 之后现象会变成 C。」
**不能被证伪的假设不是假设**，比如「可能是缓存问题」。

### 4. 一次只改一个变量

验证假设的那次改动，只动一处。同时改两处、现象好了，你不知道是哪一处起的作用，
下次还会犯。

### 5. 改完必须验证，不过就说

跑一遍原来的复现步骤。**验证不通过要直接说出来，不要改个说法糊过去**。
「应该好了」不是结论，「按原步骤跑了一遍，现在输出是 X，符合预期」才是。

## 三条纪律

- **禁止「先试试这个」式的连续改动。** 每一次改动都要先有假设。
- **找到的是原因，不是症状。** 加一个 if 绕过报错不是修好，是把问题埋深一层。
- **连续三次没修好就停下。** 再改第四次之前，回头质疑做法本身——每修一处就冒出一处
  新问题，通常是方案错了，不是这一行错了。把已经排除的可能和你的判断交回给用户，
  比编一个结论有用。
